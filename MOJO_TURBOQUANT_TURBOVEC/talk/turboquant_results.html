How Mojo closed the gap

Both fixes are standard techniques the Rust/FAISS kernels already use — ported to readable Mojo. Recall held throughout.

Mojo versionbuild ssearch ms/qrecall@1
Baseline (session 1)7.00.710.960
+ FastScan uint16/uint8 scan (b)7.00.370.959
+ Register-blocked GEMM rotation (c)0.70.380.959

(c) Rotation as a register-blocked GEMM — the naive per-vector matvec re-streamed the 9.4 MB rotation matrix for every vector (memory-bound). A comptime for micro-kernel keeps an MR×NR tile of accumulators in registers → 7.6× faster build.

# MR×NR accumulators live in registers because the
# indices are comptime (a runtime index -> stack spill)
comptime for i in range(MR):
    bch[i] = (base + (v0+i)*DIM).load[width=W](k)
comptime for j in range(NR):
    qch[j] = (Q + (d+j)*DIM).load[width=W](k)
comptime for i in range(MR):
    comptime for j in range(NR):
        acc[i*NR + j] += bch[i] * qch[j]

(b) FastScan scan kernel — cap the LUT at 127 so both nibble sub-tables combine in uint8, then one widening add into a uint16 accumulator (half the SIMD traffic of uint32), flushing before overflow → 1.9× faster search.

# combine both nibble tables in uint8 (<=254),
# one widening add into the uint16 accumulator
var s = hLUT._dynamic_shuffle(hi)
      + lLUT._dynamic_shuffle(lo)
acc16 += s.cast[DType.uint16]()
# flush acc16 -> uint32 every 256 groups

The Mojo advocacy angle

  • No BLAS dependency. Rust's speed leans on faer + gemm + nalgebra — a full linear-algebra stack. The Mojo GEMM is ~20 lines in-language and still out-builds it.
  • Data-oblivious wins on build. Fixed rotation + fixed Lloyd–Max codebook means zero training — 0.7 s vs FAISS's 16.1 s.
  • Readable, not intrinsic soup. comptime for, SIMD, parallelize, and _dynamic_shuffle express register-blocking and NEON table-lookup without dropping to assembly.
  • Remaining 2.5× on search is block width (Rust scans 32 vec/block; Mojo 16) + a proper top-k heap — known, bounded future work.

Method: DBpedia text-embedding-3-large 1536-d, 100k base / 1k queries. Metric: recall@1-in-top-k (identical harness for all three engines). 4-bit scalar quantization = 768 B/vec; FAISS IndexPQ(m=768, nbits=8, INNER_PRODUCT) matched to the same 768 B. Apple M4 Max, 16 physical cores; all three engines parallelize search across queries. Mojo recall independently cross-checked against a numpy oracle.
